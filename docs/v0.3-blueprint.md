# v0.3 实现蓝图：能力插件（Capability Providers）

> **给新会话的第一句话**：先读 `capability-hub/docs/v0.3-blueprint.md` 全文，再读它列出的「现状基线」里的文件，然后从第 13 节「开工前必须先做的 4 个验证」开始动手。
>
> 这份文档不假设读者看过之前的讨论。凡是「已验证」的结论都附了证据位置；凡是「未验证」的都会明确标注，不要在没跑过验证的情况下把它们当事实写进代码。

---

## 0. 一句话目标

让 **第三方 DSH 插件** 成为能力方案的一员：用户把某个给模型提供能力的插件「注册/接管」进能力中心，之后由**能力方案**决定它在哪些会话里生效——而不是由 profile 全局决定。

达到的效果：会话 A 有 Project Memory，会话 B 没有，两者同时运行、互不干扰。

## 1. 现状基线（v0.2，已完成）

### 1.1 代码地图

```
capability-hub/
  index.js                  Host 入口：inject 服务、初始化 store、注册 agent/created 与 agent/disposed、挂 API

  host/presets.js           纯函数层：normalizePreset、captureSkills、resolvePreset、presetDrift、effectiveSkillState
  host/providers.js         v0.3 预留：normalizeProvider / cloneProvider + 完整流程注释（本蓝图要把它变成现实）
  host/session.js           SessionRuntime：应用方案、per-agent Skill policy provider、view（来源/漂移/缺失）
  host/mcp.js               McpRuntime：ctx.loader.import('@deepseek-ai/dsh-mcp-client') + agent.ctx 挂载
```

```jsonc
    "enabled": true,

  }],
  "bundles": [],                              // v0.4 预留
  "createdAt": "ISO", "updatedAt": "ISO"
```

会话 sidecar `~/.dsh/capabilities/sessions/<sessionId>.json`：

```jsonc
{ "presetId": "preset-xxx | null", "mcp": ["mcp-id"], "skills": { "name": "state" }, "updatedAt": "ISO" }
```

`presetId === null` 表示**跟随工作区默认**，不是「没有方案」。

### 1.3 方案语义（不要重新发明）

- **应用方案 = 全量覆盖**会话的 `mcp` + `skills`。
- `skillsMode`：
  - `sparse`：方案没列出的 Skill 跟随安装状态（= `auto`）。默认方案与 v1 迁移用。
  - `explicit`：方案没列出的 Skill 视为未纳入（= `off`），UI 标「未纳入」。会话捕获的方案用。
- 会话**不会**自动跟随被改动的方案；`dirty` 由 `sameMcp` / `sameSkills` 与解析结果比对得出（不存标记）。
- 方案保留已删除的 MCP id 与未安装的 Skill 名，解析结果为 `missing`，不静默收缩。
- 漂移 = 默认方案有、本方案没有的项；会话面板提供「同步到会话」，它是一次手动调整（会让会话 dirty）。

### 1.4 API（`POST /api/capability-hub`，body 里带 `action`）

```
getSettings, getSession, saveSession, retryMcp
saveMcp, deleteMcp, deleteSkill, importSkills, scanImports
savePreset { mode: 'create' | 'update', preset }, deletePreset,
importPreset, setWorkspaceDefault, clearWorkspaceDefault
```

`saveSession` 只转发调用方真的发来的字段：**带 `presetId` 就是应用方案**，不带就是手动微调。

### 1.5 UI 现状

- **Settings**：落地 tab 是「能力方案」（列表 / 新建 / 编辑 / 导出 / 导入 / 设工作区默认），其余 tab 是 MCP / Skills / 导入。
- **会话面板**（composer chip 或 header action 打开）：方案选择器（含「跟随工作区默认 · X」）、来源徽章行（`来自 · 方案名`、`跟随工作区默认`、`已手动调整`、`缺失 N`）、漂移条 + 同步按钮、MCP 开关、Skill 三态、Model View。
- 组件风格：`h(...)` + `.ch-*` class + 宿主主题变量。所有标签都走 `t('key')`，中英字典在 `client.js` 顶层。

### 1.7 不可动摇的已拍板决策

- 个人使用，不做市场 / 团队治理。
- MCP 按会话挂载：`agent/created` 里把选中的 `dsh-mcp-client` 挂到 `agent.ctx`。
- Skills 三态 `auto / manual / off`，per-session 覆盖只允许收紧。
- 不手写 profile 的 `cordis.patch.yml`。**唯一例外**：能力插件「接管」需要把某个 entry 关掉，由 `pluginManager.setPluginEnabled` 代写一行，不手写。
- 能力插件只收**第三方**插件；DSH 原生插件是「呼吸系统」，不在管理范围。
- 三级词：**能力包（bundle）→ 能力方案（preset）→ 默认方案（default）**。
- v0.3 **只做 provider**，不碰 bundle。

## 2. v0.3 要解决的问题

以 Project Memory 为例：

1. 它现在是 profile 全局挂载的，所有会话都有，无法按会话关闭。
2. 用户想「浏览器场景」带它、「快速问答」不带。
3. 这些插件和 MCP、Skill 一样属于「模型能看到的能力」，应该出现在同一套方案里。

v0.3 之后，用户的操作变成：

> 设置 → 能力中心 → 插件能力 → 注册 `dsh-project-memory` → 选 `session-start` → 接管
> 会话面板 → 方案里勾上它 → 这个会话就有，别的会话没有。

## 3. 已验证的机制（可直接依赖，但注意每条的证据范围）

### 3.1 按 Agent（即按会话）挂载第三方插件

证据：`spike/plugin-mount-test.mjs`，报告 `spike-plugin-mount-report.json`，20/20 通过。

- 把 `dsh-project-memory` 用 `agent.ctx.plugin(module, {})` 挂到 agent scope 后：
  - 该 agent 多出 `project_memory_read / write / refresh` 三个工具；
  - 该 agent 的 system prompt 多出一段 `project-memory:snapshot`（约 2.1KB）；
  - 另一个 agent 一个工具、一段都没有；
  - 全局 assembly（`assemble({})`）也没有。
- 两个 agent 各挂一份实例：工具与 prompt 段各自独立；`fiber.dispose()` 只影响自己。
- 同一 agent 上重复挂载会抛 `tool "project_memory_read" is already registered in this scope`，不会静默双份。**但会浪费一次 apply，hub 必须先自查。**

### 3.2 事件路由是 per-agent 的

- `tools/pre-execute`：`carrier = scopeTarget(this, exec.agent)`（`dsh-tools` 第 ~3320 行）。
- `system-prompt/assemble`：`carrier = scopeTarget(this, scope)`（`dsh-system-prompt` 第 ~398 行）。
- 结论：挂在 agent scope 的监听器只对它自己那个 agent 生效。Project Memory 的写入审批闸门因此能正常工作、不串会话。

### 3.3 **`assemble` 必须传 `{ agent, scope: agent }`**

`dsh-agent` 的 `assembleContextFor(agent, signal)` 返回 `{ agent, scope: agent, signal }`。
只传 `{ scope }` 时 `assembleContext.agent` 是 `undefined`，注入型插件会**静默跳过**。

> **v0.3 第 0 步（必做）**：`host/session.js` 的 `view()` 现在调用的是 `this.ctx.systemPrompt.assemble({ scope: agent })`，要改成 `assemble({ agent, scope: agent })`，否则 Model View 永远看不到 provider 注入的 prompt 段，用户会以为插件没生效。
> **已验证（见 13.1 验证 1）**：两者实测差异明确，后者看不到 `project-memory:snapshot`。

### 3.4 插件条目寻址（`listPlugins`）

证据：`plugin_manager list_plugins` 实测（218 个 entry）。

- 每行形如 `{ entryId, moduleName, enabled, fiberPhase, patchId?, readOnlyReason? }`。
- `include:project-memory` → `patchId: "project-memory"` → **可寻址**，能 `setPluginEnabled`。
- `include:capability-hub` → `patchId: "capability-hub"`。
- 不可寻址的两种：
  - `readOnlyReason: "unaddressable"`：动态挂载的条目（例：`9dbafc41` 原生目录选择器）、根 `include`。
  - `readOnlyReason: "management-required"`：插件管理器自身、`tools`、`webserver` 等。

### 3.5 `setPluginEnabled` 是 profile 全局写

源码（`dsh-plugin-manager` 的 `index.js`）：

```js
setPluginEnabled(id, enabled) {
  const row = (await this.listPlugins()).find(item => item.entryId === id);
  if (!row) throw new ManagementFailure('unknown-plugin');
  if (row.readOnlyReason) throw new ManagementFailure(row.readOnlyReason);
  await writePluginEnabled(this.profile, row.patchId, row.moduleName, enabled);
  ...
}
// writePluginEnabled 往 profile 的 cordis.patch.yml 追加/修改：
//   - id: <patchId>
//     disabled: true
```

- 返回的变更结果带 `application` ∈ `applied | cancelled | overridden | restart-required | failed`。
- desktop profile 的 `include:hmr` 是 **active** 的，所以启停预期 `applied`（即时生效）；`restart-required` 只在 package-moved / host-module / unmanaged-plugin / module-comparison 时出现。**UI 不要假设结果，按返回的 `application` 显示。**

### 3.6 「装而不用」仍可按包名加载

证据：`spike/plugin-loader-test.mjs`，报告 `spike-plugin-loader-report.json`。

- `ctx.loader.import('dsh-project-memory')` 返回 `{ name, inject, Config, apply }`。
- 原理：DSH 在 app 里给 loader 装了 `loader.internal`，按 `baseUrl`（profile 目录）解析裸包名；独立 runtime 需要自己模拟（见 `spike/probe/resolve-hook.mjs`）。
- 所以「包仍装在 node_modules、entry 被 disable」完全不影响 hub 按名加载它。

### 3.7 静态可读的模块元数据

| 导出 | 用途 |
|---|---|
| `apply` | 必须是函数，否则不是 Host 插件（`@ace-zone/dsh-market` 只有 `default`，是纯 client bundle） |
| `inject` | 服务依赖数组，用来预判 agent scope 能否解析 |
| `Config` | Schemastery schema，可生成配置表单 |
| `name` | 插件名 |

## 4. 概念与范围

### 4.1 三个概念，v0.3 只动第一个

| 概念 | 含义 | 版本 |
|---|---|---|
| **Provider（能力提供者）** | 一个已注册的第三方插件，可以按会话挂载 | **v0.3** |
| **preset.plugins.desired** | 方案希望哪些 provider 生效 | **v0.3**（v0.2 已留字段） |
| **Bundle（能力包）** | 一个目录，把相关 MCP + Skills 打包成安装单位 | v0.4，本次不做 |

`preset.bundles` / `library.bundles` 继续只做规范化，不产生行为。

### 4.2 范围边界（明确不做）

- ❌ 不做能力包目录格式、不做 bundle 安装/更新。
- ❌ 不做 tool 级 MCP 过滤。
- ❌ 不做同一 provider 的多版本共存（一个 profile 一个版本）。
- ❌ 不做「provider 提供的 Skill」（只管 tool / prompt / resource 贡献）。
- ❌ 不接管 DSH 原生插件（`@deepseek-ai/*`）。
- ❌ 不自动改写 profile patch —— 只有用户点击「接管」时才调 `setPluginEnabled`。
- ❌ 不在会话中自动翻转 `mountAt: session-start` 的 provider。

## 5. 数据模型增量

**不需要新版本号。** v0.2 已经写了 `providers[]` 与 `preset.plugins.desired[]`，只是没人读。v0.3 只需：

1. `store.listProviders()` / `getProvider(id)` / `upsertProvider` / `deleteProvider`。
2. `preset.plugins.desired` 变成可编辑、可应用。
3. `library.providers[]` 里加一个可选字段（向后兼容，`normalizeProvider` 里补默认值）：

```jsonc
{
  "id": "provider-xxx",
  "entryId": "include:project-memory",
  "packageName": "dsh-project-memory",
  "mountAt": "session-start",
  "config": {},
  "enabled": true,
  // 新增：注册时记录的可挂载性判定结果，方便 UI 直接展示理由
  "verdict": {
    "level": "mountable | review | profile-only",
    "reasons": ["inject: tools, systemPrompt", "no provided services (unverified)"],
    "checkedAt": "ISO",
    "dshVersion": "0.2.2-rc.1"
  },
  "createdAt": "ISO", "updatedAt": "ISO"
}
```

`verdict` 只是**缓存**，不是真相；每次注册/重新检查时重算。

### 5.1 注册即默认生效（落地修订）

用户装上插件、又把它注册成能力，意图就是「它应该生效」。所以注册成功后：

- provider 记录 `enabled: true`（不变）；
- **新注册的 provider 自动加入默认方案**（`default.plugins.desired`），规则与 `upsertMcp`
  把新 MCP 吸收进默认方案完全一致：只有当默认方案原本就包含**全部已注册 provider**时才追加；
  用户已经手工裁剪过基线（少了某一项）就不再自动塞入，避免「删掉的又被加回来」。
- 于是跟随工作区默认的新会话开箱就有它；想按会话裁剪的人再自己调。

`provider.issue`（v0.3 补充）记录挂载失败证明的永久事实，目前只有 `global-resource`
（注册进程级资源，只能有一个实例），见 §9.1。

### 6.2 `host/capability-catalog.js`（新文件）

职责：把 `pluginManager` 与 loader 的原始信息，翻译成 UI 能用的「候选能力插件」。

```js
export class CapabilityCatalog {
  constructor(ctx) { this.ctx = ctx; }

  manager() {
    const manager = this.ctx.get?.('pluginManager');
    if (!manager) throw new Error('pluginManager 服务不可用');
    return manager;
  }

  /** 所有 entry，附上「是否第三方」「是否可寻址」「是否已注册」。 */
  async list() { /* manager.listPlugins() + 过滤 + 标注 */ }

  /** 静态体检：加载模块，读 apply / inject / Config。 */
  async inspect(packageName) {
    const module = await this.ctx.loader.import(packageName);
    return {
      hasApply: typeof module.apply === 'function',
      inject: Array.isArray(module.inject) ? module.inject : [],
      hasConfig: module.Config !== undefined,
    };
  }

  /** 三档判定，见第 8 节。 */
  async judge(entry) { /* 静态 → 探针 → 隔离，逐级降档 */ }

  async takeover(entry, { mountAt, config }) { /* setPluginEnabled(entryId, false) + 写 store */ }
  async release(provider) { /* setPluginEnabled(entryId, true) + 删 store 记录 */ }
}
```

**第三方判定**（按可靠性排序，实现时三条都留）：

1. profile 的 `package.json` → `dependencies` 里出现，且解析路径在 `profiles/<name>/node_modules` 下。profile 目录可从 `ctx.loader.baseUrl`（`file:///.../profiles/desktop/`）取。
2. 兜底：`manager.listBundles()` 里 `removable === true` 的 bundle。
3. 最后兜底：模块名不以 `@deepseek-ai/` 开头。

> ⚠️ `ctx.loader.baseUrl` 是否在插件 ctx 上可读，**未验证**。开工前先 `console.log` 一次确认（见第 13 节验证 4）。
> **已验证（见 13.1 验证 4）**：`ctx.loader.baseUrl` 是 `undefined`；用 `ctx.baseUrl`（= profile 目录 URL）。

### 6.3 `host/session.js`（改动 4 处）

```js
// 1) onCreated：先挂 MCP，再挂 provider（顺序见 7.2）
async onCreated(agent) {
  ...现有逻辑...
  await this.mcp.apply(agent, state, this.store.library);
  await this.mountProviders(agent, record);
}

// 2) mountProviders
async mountProviders(agent, record) {
  const preset = this.store.resolvePresetFor(record.cwd, record.state.presetId);
  const desired = new Set(
    preset.plugins.desired.filter(item => item.enabled).map(item => item.providerId),
  );
  const catalog = new CapabilityCatalog(this.ctx);
  const globals = await catalog.list();           // 一次性取，判断「已全局启用」
  for (const provider of this.store.listProviders()) {
    if (!desired.has(provider.id) || !provider.enabled) continue;
    if (provider.mountAt === 'session-start' && record.started) continue;  // 太晚，跳过并记录 deferred

    const row = globals.find(item => item.entryId === provider.entryId);
    if (row?.enabled === true) {
      // 没有接管就挂，会得到双份工具/段落
      record.providers.set(provider.id, { status: 'failed', error: '仍由 profile 全局启用，请先接管' });
      continue;
    }
    try {
      const module = await this.ctx.loader.import(provider.packageName);
      const fiber = agent.ctx.plugin(module, provider.config);
      await fiber;                                  // 加超时，见第 9 节
      // await 成功不代表挂载成功：缺服务时 `await fiber` 会立刻 resolve 而 state 仍是 0。
      // 见 13.1 验证 3 —— 必须以 fiber.state === 2 判定，否则要报「在等待服务」并点名。
      record.providerFibers.set(provider.id, fiber);
      record.providers.set(provider.id, fiber.state === 2 ? { status: 'mounted' } : { status: 'failed', error: ... });
    } catch (error) {
      record.providers.set(provider.id, { status: 'failed', error: String(error?.message ?? error) });
    }  }
}

// 3) update：presetId 变化后重新计算 provider 差异
//    - 新方案要的、当前没挂的 → 若 mountAt === 'any-time' 才挂，否则记 deferred
//    - 当前挂了、新方案不要的 → 若 mountAt === 'any-time' 才卸，否则记 locked

// 4) view：新增 result.providers（见第 10.2 节）
```

**关键状态字段**（放 `record` 内部，不持久化）：

```
record.started            boolean   首轮是否已开始（agent/created 之后、第一次 turn 之前为 false）
record.providerFibers     Map<providerId, Fiber>
record.providers          Map<providerId, { status, error }>
```

`record.started` 的判定方法：v0.3 可以简单地在 `agent/created` 结束时置 `true`（此时第一轮尚未发生，挂载已经完成）；真正严格的判定需要 hook `agent/pre-step`，属于增强项，见第 14 节。

### 6.4 `host/store.js`（新增方法）

```js
listProviders() / getProvider(id)
async upsertProvider(input)     // id 由 entryId 派生，一个 entry 只能注册一次
async deleteProvider(id)
async setProviderEnabled(id, enabled)
```

`upsertProvider` 要求 `entryId` 唯一；如果同一 `entryId` 已注册，返回已存在的记录而不是新建（避免重复 provider）。

### 6.5 `host/api.js`（新增 action）

```js
// 只读
async listCapabilityPlugins()          // catalog.list()：候选 + 已注册状态
async inspectCapabilityPlugin({ entryId })
// 生命周期
async registerProvider({ entryId, mountAt, config })
async unregisterProvider({ id })
async setProviderEnabled({ id, enabled })
async recheckProvider({ id })          // 重跑第 8 节判定，刷新 verdict
// 会话
// saveSession 已支持；新增 provider 开关的会话级操作：
async setSessionProviders({ sessionId, providerIds })   // 等价于改会话的 plugins 选择
```

**会话侧的选择存在哪里？** 两个选项：

- **A（推荐）**：会话不单独存 provider 选择，只存 `presetId`；provider 开关只是「应用方案 / 更新方案」的输入。手动开启某个 provider = 把 `providerId` 加进会话状态，需要额外字段。
- **B**：给会话 sidecar 加 `plugins: { desired: [...] }`，与 preset 同构。

建议 **B**：会话已经有独立的 `mcp` / `skills`，加 `plugins` 保持三者对称，`dirty` 判定也统一。这意味着 `normalizeSession` 与 `buildSessionState` 各加一个字段。

### 6.6 `client.js`（新增两块 UI）

1. **Settings → 插件能力 tab**
   - 已注册列表：名称 / entryId / `mountAt` 徽章 / 状态 / 判定档位 / 编辑 / 释放。
   - 「注册能力插件」向导（3 步，见 7.1）。
   - 空白态：解释「为什么只列第三方插件」。
2. **会话面板 → 插件能力区**
   - 每行：名称、`session-start` 锁图标、状态徽章（已挂载 / 失败 / 待下次会话）、开关。
   - `mountAt === 'session-start'` 且会话已开始 → 开关禁用，提示「本会话开始时已确定」。
3. **方案编辑器**：`plugins.desired` 勾选区，与 MCP / Skills 并列。

## 7. 关键流程

### 7.1 注册 / 接管（向导）

```
Step 1  选择插件
        列出第三方 entry（catalog.list() 过滤）
        └ 已经有 provider 用这个 entry → 显示「已注册」并禁止再选

Step 2  体检（catalog.judge）
        展示三档结论 + 理由 + 实际贡献预览
        └ profile-only → 只允许「登记为参考」，不允许接管

Step 3  配置
        mountAt：默认 session-start
        config：有 Config schema 时生成表单，否则给 JSON 文本框
        └ session-start 要解释：会话中途不能切换，可避免 prompt 缓存失效

Step 4  接管确认（危险动作，必须显式）
        文案要点：
        - 会把这个插件从「全局启用」改为「由能力方案管理」
        - 之后所有会话都必须显式选到它才有
        - 会写一行到 profile 的 cordis.patch.yml（由插件管理器代写）
        - 返回 restart-required 时如实告知
        └ 确认后：manager.setPluginEnabled(entryId, false) → store.upsertProvider
```

**接管失败的回滚**：如果写 provider 失败，要尝试 `setPluginEnabled(entryId, true)` 恢复；失败也要记日志并如实报错。

### 7.2 会话挂载顺序

```
agent/created
  ├ 1. 解析方案（presetId ?? 工作区默认 ?? default）
  ├ 2. 建 record（state / preset / started=false）
  ├ 3. installPolicy（Skill provider）
  ├ 4. mcp.apply（MCP 挂载）
  ├ 5. mountProviders（能力插件）
  └ 6. started = true
```

顺序理由：provider 可能提供工具 → 工具的 `tools/pre-execute` 闸门要先在；provider 也可能影响 prompt → 要在第一次 assemble 之前完成。MCP 与 provider 之间无强依赖，先 MCP 是因为它已有成熟的重试/状态机制。

### 7.3 会话中切换

| `mountAt` | 新方案要它 | 新方案不要它 |
|---|---|---|
| `session-start` | `deferred`（提示下次会话） | `locked`（本会话继续保留，提示下次会话生效） |
| `any-time` | 立即挂载 | 立即 dispose |

**不要在会话中途直接卸载 `session-start` 的 provider**：它注入的 prompt 段消失会让本会话前后半段的「世界观」不一致，并且击穿 KV cache。

### 7.4 释放（把插件还给 profile）

```
manager.setPluginEnabled(entryId, true)
store.deleteProvider(id)
从所有 preset.plugins.desired 中移除该 providerId（并提示哪些方案被改动）
```

### 7.6 实现时的两处偏离（v0.3.0 落地记录）

**偏离 1 · 挂载与否看「会话状态」，不看「方案」。**
7.3 的表写成「新方案要它 / 不要它」，但 v0.2 起会话就持有自己的一份 `mcp` / `skills` 副本，
方案只是应用时的初值。provider 因此与它们对称：`SessionRuntime.applyProviders` 读
`state.plugins.desired`（第 6.5 节选项 B 的字段），预设只决定「应用方案时写进会话什么」。
这样「会话手动加一个 provider」不需要额外字段，`dirty` 也自然成立。
`view().providers[].desired` 同样表示会话的选择；是否偏离方案由 `preset.dirty` 表达。

**偏离 2 · 探针不做「临时 agent scope 里挂一次」，改成两个更便宜的观察点。**
第 8 节 Step 2 原计划在临时 scope 里挂一次看贡献。实现时放弃了，原因不是偷懒：

- 真正隔离的临时 scope 需要 `dsh-scope` 的 `createScope`；在插件里第二次加载该包会得到另一个
  scope 注册表，`tools/schemas` 与真实 agent 不共享，观察结果不可信；
- 挂在真实会话上再 dispose，会与那个会话正在跑的 turn 抢工具注册（且第 3.1 节的实验证明重复
  挂载会抛错）。

改用两个**零副作用**的观察点：

1. `inject` 可解析性：直接问一个真实 agent 的 `agent.ctx.get(name)`（结论精确到服务名），
   没有活着的会话时才退回已知服务白名单，未知的一律降档 `review`。
2. 贡献：**在真实挂载前后各取一次** `tools.schemas(agent)` 与 `assemble({agent, scope})`
   的差集，写进 `record.providers[id].contributions`，从 Model View 与面板露出。
   这比「先探针再挂」少挂一次，也顺带覆盖了「声明了但没贡献」的情况。

### 7.7 实现备注（不是偏离，但值得写下来）

- 挂载成功的判定是 `fiber.state === 2`，不是 `await fiber`（13.1 验证 3）。
- 面板的「重新挂载」调用 `remountProviders`，它按 `initial: true` 重跑一遍 provider 通道：
  这是第 14 节「HMR 重载后状态丢失」的处置，也是接管后让某个运行中会话重新拿到插件的唯一手段。
- 释放（`unregisterProvider`）会先把各会话里的 per-agent 实例 dispose，再让 entry 恢复全局启用；
  否则同一份插件会既有全局实例又有实例副本，工具注册直接抛错。

### 7.5 fork / subagent

- 现有逻辑：子 agent 走 `store.copySession(parent)`，继承父会话的 `presetId` 与 state。
- provider 挂载在子 agent 自己的 `onCreated` 里重新执行一遍（各自一份实例）。
- **需要验证**：Project Memory 在子会话里的行为（它自己会跳过 child session 的审批闸门，见 `approval-gate.js` 的 `isChildSession`）。这条属于行为观察，不是阻塞项。

## 8. 可挂载性判定（三档）

产出必须是一个**结论 + 理由**，不是布尔值。理由要能直接给用户看。

### Step 1 · 静态（零副作用）

| 检查 | 来源 | 不通过的含义 |
|---|---|---|
| 有 `apply` 函数 | `loader.import(packageName)` | 不是 Host 插件（纯 client bundle）→ **profile-only** |
| `inject` 能在 agent scope 解析 | 对照白名单 | 依赖 host 专属服务 → **profile-only** |
| 包是第三方 | 6.2 的三条判断 | 原生插件 → 不列出 |
| entry 可寻址 | `listPlugins()` 的 `patchId` | `unaddressable` / `management-required` → **profile-only**（不能接管） |

agent scope 已知可解析的服务（实测过 / 有先例）：`tools`、`systemPrompt`、`skills`、`approval`、`agents`。
**未验证**：`sessionProjections`、`session`、`fs`、`subprocess`。遇到不认识的 `inject` → 判 **review**，不要判 profile-only。

### Step 2 · 探针挂载（一次性，可回滚）

在临时 agent scope 里挂一次，观察：

- 注册了哪些 tool（`ctx.tools.schemas(agent)` 前后差集）
- 有没有往 prompt 里加段（`assemble({ agent, scope: agent })` 前后差集）
- 有没有注册 Skill provider

**没有任何贡献** → 标「已注册但未观察到贡献」，仍允许但警告。这同时是「声明了但没用」的自查。

探针要有超时（建议 10 秒）和独立 ctx，用完 dispose。

### Step 3 · 隔离探针（可选，默认关）

两个 agent 各挂一次、各触发一次，检查是否互相影响。开销大，只在「用户要求重新检查」时执行。

### 三档结论

| 档位 | 含义 | UI |
|---|---|---|
| `mountable` | 三档都通过 | 默认推荐 |
| `review` | 静态通过，但有未知 `inject` 或探针有异常 | 允许，标「需人工确认」 |
| `profile-only` | 不能按会话挂载 | 只能查看，不能注册 |

**永远不要**因为这档判定而阻止用户在会话里手动观察结果——判定是预判，Model View 才是真相。

## 9. 错误与降级

| 场景 | 行为 |
|---|---|
| `pluginManager` 服务不可用 | 整个插件能力 tab 显示「当前 DSH 版本不支持」，其他功能不受影响 |
| 加载模块失败 | provider 状态 `failed`，错误原文进会话面板；不影响会话启动 |
| 挂载超时（默认 10s） | 记为 `failed` + 提示「重试」，不阻塞第一轮 |
| 模块 `inject` 解析失败 | `failed`，错误里给出缺的服务名 |
| 仍被 profile 全局启用 | `failed`，提示「先接管」 |
| 同一 agent 上重复挂载 | 不会发生（hub 先自查）；万一发生，工具注册会抛错，捕获后记 `failed` |
| 接管返回 `restart-required` | 明确告诉用户「需要重启 DSH，重启前它可能仍在全局生效」 |
| 接管返回 `overridden` | 告诉用户「被更高优先层覆盖，实际未生效」 |
| 方案引用已删除的 provider | `missing`，会话面板列出，不影响其他能力 |
| **插件注册进程级资源（HTTP 路由 / 端口）** | 第二个会话挂载时抛 `webserver: duplicate exact route "…"`。捕获后**分类为 `global-resource` 并持久化到 `provider.issue`**，错误文案说明「只能有一个实例」；之后的会话再尝试会直接点名占用者（`Already mounted in session <id>`），不再让插件抛原始错误。见 9.1 |

## 9.1 进程级资源：这一类插件不能按会话挂载

**症状**：会话面板显示 `挂载失败`，错误原文 `webserver: duplicate exact route "/wiki/tree"`。

**机制**（三处证据）：

1. `dsh-llm-wiki` 在 `apply()` 里注册三条**固定路径**的 exact route ——
   `lib/browser/wiki-http.js:248–299`，`WIKI_TREE_ROUTE` / `WIKI_PAGE_ROUTE` / `WIKI_STAGED_ROUTE`，
   走的是 `ctx.get('webServer', false)`（注意：`inject` 只有 `['tools','systemPrompt']`，**静态查不出来**）。
2. `@deepseek-ai/dsh-host-webserver` 的 `register()` 只有一个进程级路由表：
   `if (table.has(route.path)) throw new Error('webserver: duplicate ' + route.kind + ' route …')`
   （`lib/index.js:375–382`）。路由表**不是按 Agent scope 隔离的**，注释里也写明
   「route patterns are a composition-level contract」。
3. 同一个服务器进程里只要有第二份实例（另一个会话在 `agent.ctx` 上又挂了一份），第二条 `/wiki/tree`
   就撞车；`tryRegister` 没有 try/catch，异常穿过 `ctx.effect(body)` → fiber 变 failed →
   `applyProviders` 收到 reject。

所以：**注册进程级资源的插件天然只能有一个实例**。`mountAt: any-time` 只是让它更容易撞：
两个会话都勾上，第二个必失败。

**v0.3 的处置**（已实现，`spike/provider-mount-test.mjs` I1–I5 覆盖）：

- 挂载失败时按错误文本分类（`providers.js` 的 `classifyMountError`）：
  `duplicate (exact|prefix|upgrade) route`、`EADDRINUSE` → `global-resource`；
  `already registered in this scope` → `already-mounted`（防御性，正常不该出现）。
- `global-resource` 写进 `provider.issue`（持久化），错误文案换成
  「这个插件注册了进程级资源，同一时刻只能有一个实例；要么释放回全局，要么只在一个会话里用」。
- 之后任何会话再尝试挂载时，`applyProviders` 先查「别的会话是否正持有它」：
  持有 → 直接报 `Already mounted in session <id>`，不再让插件抛原始错误。
  （这条排他检查**只对已知 `global-resource` 的 provider 生效**——`dsh-project-memory`
  这类 scope 安全插件仍然允许两个会话各挂一份，20/20 实验已证。）
- 挂载成功即清除 `issue`；设置页「重新检查」也会先清除再重试。
- UI：设置页行上打 `全局资源型` 红标 + 处置提示；会话面板在错误下方给出同一句提示。

**给用户的结论**：`dsh-llm-wiki` 这种插件不适合按会话分配。想要「所有会话都有 wiki」，
就在设置页把它**释放**，让它回 profile 全局运行——那是它原本的设计。按会话开关只对
scope 安全的插件（工具 / prompt 段 / 自带 provider 注册）成立。

### 13.1 验证结果（2026-11-08，已跑完，实现按这些结论来）

证据：`spike/provider-probe.mjs`，报告 `spike-provider-probe-report.json`
（`node --import ./spike/probe/register.mjs spike/provider-probe.mjs`，12/12 通过）。

#### 验证 1 · `assemble` 的 `agent` 参数 —— **必须修**

在真实 `dsh-project-memory` 上实测（同一个 agent）：

| 调用 | 段落 |
|---|---|
| `assemble({ agent, scope: agent })` | `harness:identity` · `deployment:persona-prefix` · **`project-memory:snapshot`** · `deployment:persona-suffix` |
| `assemble({ scope: agent })` | 无 `project-memory:snapshot` |
| `assemble({})` | 无 |

→ 3.3 的修复是**必须**的：`host/session.js` 的 `view()` 必须传 `{ agent, scope: agent }`。
另外这条也解释了「插件装了却没反应」的常见假象：`assembleContext.agent === undefined` 是**静默**
跳过，`project-memory` 不会报错，只是不注入。

#### 验证 3 · `agent.ctx.plugin()` 缺服务时的行为 —— **不 reject、不悬挂、静默不激活**

| 情况 | `await fiber` | `fiber.state` | `apply` 是否执行 |
|---|---|---|---|
| `inject: ['tools', 'missingService']` | **立刻 resolve，不抛错** | `0`（pending） | **否** |
| `apply()` 抛错 | reject，错误原文 | `3`（failed） | 是（抛之前） |
| 正常插件 | resolve | `2`（active） | 是 |

`fiber.state` 取值：`0` pending / `2` active / `3` failed / `4` disposed。

→ **`await fiber` 成功 ≠ 挂载成功**。挂载后必须检查 `fiber.state === 2`，否则当作失败：
「插件在等待服务，未生效」。缺哪个服务可以算出来：`Object.keys(fiber.inject)` 里
`agent.ctx.get(name) === undefined` 的那些（实测 `tools → true`、`missingService → false`）。

→ 第 9 节的超时逻辑因此改成：`await` 仍加超时（防止 apply 内部悬挂），但**判定成功以 `state` 为准**。

#### 验证 4 · profile 目录从哪读 —— **`ctx.baseUrl`，不是 `ctx.loader.baseUrl`**

| 表达式 | 值 |
|---|---|
| `ctx.baseUrl` | `file:///…/.dsh/profiles/desktop/` ✅ |
| `ctx.loader.baseUrl` | `undefined`（服务对象上没有这个属性） |
| `ctx.loader.ctx.baseUrl` | 同上 URL（能读，但绕了一层） |
| `ctx.loader.internal.import` | 存在（`typeof === 'function'`） |

依据：`app-boot` 的 `boot()` 先 `ctx.baseUrl = pathToFileURL(dirname(absoluteConfigPath)).href + "/"`，
再 `ctx.plugin(Loader)`（**不传 config**）；`cordis-plugin-loader` 的 `EntryTree` 用
`ctx.extend({ baseUrl: ctx.baseUrl })` 把 baseUrl 传进子树，所以插件 ctx 继承得到。

→ 6.2 的第三方判定用 `ctx.baseUrl` + `fileURLToPath` 得到 profile 目录。

#### 验证 2 · 关掉一个正在运行的 entry —— 源码结论（未做活体实验）

**没有做活体实验的原因**：这条要求 `setPluginEnabled('include:project-memory', false)`，而
`pluginManager` 只存在于运行中的 app 进程里；副本 profile 无法用脚本跑起完整 app runtime。
活体实验的唯一形式是在**主 profile** 上真的把 `dsh-project-memory` 关掉，那会改动用户正在用的
DSH，属于不可接受的副作用。结论改由源码给出，证据位置附后。

`dsh-plugin-manager/lib/index.js`：

- `setPluginEnabled(id, enabled)` → `writePluginEnabled(profile, row.patchId, row.moduleName, enabled)`
  → `reload(enabled ? [row.patchId] : [])`（`index.js` 第 2669–2682 行）。
- `change()` 初始化 `application`：**有 `hmr` 服务 → `'applied'`**，没有 → `'restart-required'`
  （`restartReason: 'no-hmr'`）（第 3164–3171 行）。
- `reload()` → `hmr.reconcileProfile(requiredIds)`；返回带 `restartReason` 时改判 `restart-required`
  （第 3129–3141、3172–3183 行）。`restartReason` 只有两个来源：`package-moved`
  （`app-boot` 第 4588–4592 行）和 `module-comparison`（`dsh-hmr` 第 1368 行）。
- `setPluginEnabled` 在 reload 之后重新读 `listPlugins()`，若该行的 `enabled` 仍不等于请求值且
  `hmr` 存在 → 返回 **`'overridden'`**（第 2676 行）。

`dsh-hmr/lib/index.js` 的 `reconcileProfile()` → `app-boot` 的 `recomposeProfile()`
→ `entry.update({ config: { ...includeConfig, patches } })`，随后
`await Promise.allSettled(previousFibers.map(fiber => fiber.await()))` + `await ctx.loader.await()`
（`app-boot` 第 4601–4609 行）。

**结论**：

1. 桌面 profile 的 `hmr` 存在 → 接管预期 `application: 'applied'`，**立即生效，不需要重启**。
2. 「立即生效」意味着**正在运行的会话立刻失去该插件的贡献**：entry 的 fiber 被 dispose，
   它注册在全局 scope 的 tool 与 `system-prompt/assemble` 监听器一起消失。
   - 已经发出的一轮请求不受影响（prompt 已组装）；
   - 之后的 assembly 与 `tools.schemas()` 立刻看不到它。
3. 所以**接管是在运行中改变全局能力的动作**，UI 必须写明：「正在运行的会话会立即失去它；
   要让某个会话继续使用，请把它加进方案并**重开会话**」。
   v0.3 的实现选择：接管**不阻止**，但登记完成后主动提示受影响的活跃会话数，并在会话面板提供
   「重新挂载」（见第 14 节那条开放问题的处置）。

> 第 9 节表格里「接管返回 `restart-required`」那一行因此保留，但实际只在 `no-hmr` 或
> package-moved / module-comparison 时出现，UI 按返回的 `application` 显示，不预设。

## 14. 风险与开放问题

| 风险 | 现状 | 建议 |
|---|---|---|
| 探针测不出「模块级全局状态」 | 已知 | 判定分三档，不承诺绝对安全；文档里写明 |
| 一个 bundle 可能 insert 多个 entry | 结构上可能 | 注册粒度用 entryId，不假设一包一行 |
| 原生 vs 第三方判定可能误判 | 三条兜底 | 注册向导显示判定依据，允许用户手动覆盖（覆盖要留痕） |
| `mountAt` 由用户选，可能选错 | 用户决策 | 默认 `session-start`；选 `any-time` 时警告 |
| 接管绕过 `danger-full-access` 审批 | 插件内直接调服务不触发审批 | UI 点击即授权；但要在确认框里写清后果。是否改走 `ctx.get('approval')`，属于待定项 |
| `record.started` 判定粗糙 | 简化实现 | 增强项：监听 `agent/pre-step` 精确判定首轮 |
| HMR 重载后 provider 状态丢失 | 未验证 | 依赖 `agent/created` 重建；已存在会话可能停留在旧状态，需要在 UI 上留一个「重新挂载」按钮 |
| 同一个 entry 先注册再被用户手动全局启用 | 可能出现 | 挂载前始终检查 `row.enabled`，发现就报错而不是双挂 |

### 15.5 与 Project Memory 相关的事实

- `inject: ['tools', 'systemPrompt']`，**不 provide 任何服务**，状态全在 `<workspace>/.agent/MEMORY.md`。
- 两个 waterfall：`system-prompt/assemble`（注入段落）、`tools/pre-execute`（写入审批）。
- prompt 段名固定为 `project-memory:snapshot`，插入前会过滤同名段（所以重复挂载不会出现两段，但会浪费一次 apply）。
- 写盘有 mkdir 锁 + revision CAS，两个实例并发写是安全的（一个 `updated`、一个 `conflict`）。
- 即使工作区没有 `MEMORY.md`，它也会注入一段「应当创建记忆」的指令 —— 所以「这个会话启用 memory」不等于只读开关。
